USER MANAGEMENT AND AUTHENTICATION SYSTEM GUIDE
================================================

Purpose
-------
This document describes the authentication, authorization, users, roles,
privileges, menus, refresh-token sessions, and related API endpoints as they
are currently implemented in this NestJS + MongoDB project.

This is an implementation guide, not a statement of ideal behavior. The final
section lists security issues and recommended improvements.


1. TECHNOLOGY AND HIGH-LEVEL ARCHITECTURE
------------------------------------------

The application uses:

- NestJS and TypeScript for the HTTP API.
- MongoDB with Mongoose for users, roles, menus, privileges, and refresh sessions.
- bcrypt for password hashing and refresh-token hash storage.
- Passport JWT for bearer access-token authentication.
- An httpOnly cookie for the refresh token.
- MongoDB transactions for refresh-token rotation and revocation.
- DTO validation through class-validator and a global ValidationPipe.

Main modules:

- auth: signup, login, refresh, logout, logout-all, JWT strategy and guards.
- users: user creation, profile, user administration.
- roles: roles, admin flag, and menu assignment.
- privelleges: privilege records and CRUD operations.
- menu: hierarchical menu management.
- labels: label CRUD (currently not protected by authentication).

The relationship between the main security objects is:

    User
      |
      +--> one Role
              |
              +--> isAdmin flag
              +--> menuIds[] --> Menu documents
              +--> privelleges[] --> Privelleges documents

Important current behavior:

- The access token contains the user's role ID/value at token issue time.
- AdminGuard loads that role from MongoDB and checks role.isAdmin.
- The current code does not use individual privileges to authorize endpoints.
- User menu data is built by UsersService.findById and returned by
  GET /users/myprofile.


2. CONFIGURATION
----------------

Relevant environment variables:

- PORT: HTTP port; defaults to 3000.
- MONGODB_URI: MongoDB connection string.
- JWT_SECRET: secret used to sign and verify both JWT types.
- JWT_EXPIRES_IN: access-token lifetime; README default is 15m.
- JWT_REFRESH_EXPIRES_IN: refresh-token lifetime; README default is 7d.
- BCRYPT_SALT_ROUNDS: bcrypt cost; defaults to 10.

The application currently has a development fallback JWT secret when JWT_SECRET
is absent. This must not be used in production.

MongoDB must run as a replica set for the transaction-based refresh rotation,
logout, and logout-all operations. A standalone MongoDB instance is not enough.


3. REQUEST VALIDATION AND COMMON HTTP BEHAVIOR
-----------------------------------------------

main.ts configures:

- cookie-parser, so request.cookies is available.
- Global ValidationPipe with whitelist, forbidNonWhitelisted, and transform.
- A global HTTP exception filter.
- CORS with credentials enabled. The current origin setting reflects origins
  and should be restricted in production.

Validation behavior:

- Unknown DTO fields are rejected.
- Invalid DTO fields return a validation error.
- Passwords, raw access tokens, and raw refresh tokens must not be logged.


4. DATA MODELS
--------------

4.1 User
~~~~~~~~

Collection/model: Users

Fields:

- _id: MongoDB user identifier.
- name: optional display name.
- email: required, unique, lowercased, trimmed email.
- password: required bcrypt hash; never return this to clients.
- role: required ObjectId reference to Roles.
- userStatus: active, inactive, or banned; defaults to active.
- createdAt and updatedAt.

4.2 Role
~~~~~~~~

Collection/model: Roles

Fields:

- _id: role identifier.
- name: required and unique.
- isAdmin: boolean; defaults to false.
- menuIds: array of Menu ObjectIds.
- privelleges: array of Privelleges ObjectIds.

4.3 Menu
~~~~~~~~

Collection/model: Menu

Fields:

- title: display title.
- slug: globally unique slug.
- type: TAB, SECTION, SUBSECTION, or PAGE.
- parentId: optional parent menu ID.
- ancestors: array of ancestor menu IDs.
- isActive: boolean; defaults to true.
- order: sibling ordering value.
- icon: optional icon value.

Allowed menu hierarchy:

- TAB has no parent.
- SECTION must be under TAB.
- SUBSECTION must be under SECTION.
- PAGE may be under TAB, SECTION, or SUBSECTION.

4.4 Privilege
~~~~~~~~~~~~~

Collection/model: Privelleges (the spelling is part of the current code).

Fields:

- _id
- name

Privilege records and role references exist, but no guard currently checks a
specific privilege before allowing an endpoint.

4.5 Refresh-token session
~~~~~~~~~~~~~~~~~~~~~~~~~

Collection: refresh_tokens

Fields:

- userId: owner.
- tokenHash: bcrypt hash of the raw refresh JWT; excluded from normal queries.
- jti: unique refresh-token ID.
- familyId: identifies all rotated tokens from one login/session family.
- ipAddress and lastIpAddress: session metadata.
- userAgent and deviceName: client/device metadata.
- lastUsedAt: last successful login/refresh time.
- expiresAt: session expiry, with a MongoDB TTL index.
- revokedAt and revokedReason: revocation audit fields.

The raw refresh token is not stored in MongoDB.


5. TOKEN TYPES AND CLAIMS
-------------------------

5.1 Access token
~~~~~~~~~~~~~~~~

The access token is a signed JWT returned in the login and refresh response
body. The client sends it on protected requests:

    Authorization: Bearer <access-token>

Claims issued by AuthTokenService:

    {
      "sub": "user-id",
      "email": "user@example.com",
      "role": "role-id",
      "timezone": "Asia/Karachi",
      "iat": 0,
      "exp": 0
    }

The exact iat and exp values are generated by JWT. The access-token lifetime is
JWT_EXPIRES_IN, normally 15 minutes.

JwtStrategy extracts the bearer token, verifies its signature using JWT_SECRET,
and exposes this request user object:

    {
      userId: payload.sub,
      email: payload.email,
      role: payload.role,
      timezone: payload.timezone
    }

The access token is stateless. Revoking a refresh session does not immediately
invalidate already-issued access tokens; they remain valid until expiration.

5.2 Refresh token
~~~~~~~~~~~~~~~~~~

The refresh token is a separate signed JWT. Its claims are:

    {
      "sub": "user-id",
      "type": "refresh",
      "jti": "unique-token-id",
      "iat": 0,
      "exp": 0
    }

It is sent only as an httpOnly cookie named refreshToken. It is not returned in
the JSON response body. The refresh-token lifetime is JWT_REFRESH_EXPIRES_IN,
normally 7 days.


6. COMPLETE LOGIN FLOW
----------------------

Endpoint:

    POST /auth/login

Request headers and body:

    Content-Type: application/json

    {
      "email": "user@example.com",
      "password": "Password@123",
      "timezone": "Asia/Karachi",
      "deviceName": "Chrome on Windows"
    }

timezone and deviceName are optional. The service defaults timezone to
Asia/Karachi when it is omitted.

Server flow:

1. AuthController validates the DTO.
2. AuthService searches for the user by email.
3. bcrypt compares the supplied password against user.password.
4. If the user does not exist or the password is wrong, the API returns an
   invalid-credentials error.
5. AuthTokenService creates an access token.
6. AuthTokenService creates a refresh JWT with a new random UUID jti.
7. The refresh token expiry is decoded and converted to a Date.
8. RefreshTokenService bcrypt-hashes the raw refresh token.
9. A refresh_tokens session is stored with jti, familyId, expiry, and metadata.
   On initial login familyId equals the first refresh-token jti.
10. The controller sets the refreshToken cookie.
11. The controller returns the user and access token, but removes the refresh
    token from the JSON body.

Response shape:

    {
      "user": { "...": "user document fields" },
      "accessToken": "eyJ..."
    }

Cookie currently configured by the controller:

    refreshToken=<jwt>; HttpOnly; Path=/; Max-Age=604800; SameSite=Lax

secure is currently false in source code and must be true over HTTPS in
production.

Client responsibilities after login:

- Keep the access token in memory where possible.
- Do not place the refresh token in localStorage, sessionStorage, Redux, or
  other JavaScript-readable storage.
- Send the access token as a Bearer header.
- Send credentials/include for cookie-based refresh requests.


7. COMPLETE ACCESS-TOKEN AUTHENTICATION FLOW
--------------------------------------------

For a protected endpoint:

1. The client sends Authorization: Bearer <access-token>.
2. JwtAuthGuard invokes Passport's jwt strategy.
3. The strategy extracts and verifies the JWT signature and expiry.
4. On success, JwtStrategy.validate maps claims to request.user.
5. The controller can use request.user.userId, email, role, and timezone.
6. On missing, invalid, or expired access token, the request is rejected.

Example:

    GET /users/myprofile
    Authorization: Bearer eyJ...

JwtAuthGuard proves authentication (who supplied the token). It does not by
itself prove that the user is an administrator or has a particular privilege.


8. ADMIN AUTHORIZATION FLOW
---------------------------

Admin-protected endpoints use:

    @UseGuards(JwtAuthGuard, AdminGuard)

Execution order:

1. JwtAuthGuard authenticates the bearer token.
2. AdminGuard reads request.user.role.
3. AdminGuard loads the role document from MongoDB.
4. If the role is missing or invalid, access is forbidden.
5. If role.isAdmin is false, access is forbidden.
6. If role.isAdmin is true, the endpoint executes.

This is database-backed role checking, so changing role.isAdmin can affect
future requests even though the role value in an existing JWT is unchanged.

Current limitation: AdminGuard checks only isAdmin. It does not check
role.privelleges or a route-specific permission.


9. REFRESH-TOKEN ROTATION FLOW
------------------------------

Endpoint:

    POST /auth/refresh

Request:

- No JSON body.
- Browser must send the refreshToken cookie.
- For fetch, use credentials: 'include'.

Server flow:

1. Controller reads request.cookies.refreshToken.
2. AuthTokenService verifies the JWT signature and expiry.
3. The service requires type=refresh and a jti claim.
4. The user is loaded by payload.sub.
5. The user must currently have userStatus=active for refresh to continue.
6. A replacement access token and replacement refresh token are issued.
7. RefreshTokenService starts a MongoDB transaction.
8. It loads the session by userId and presented jti, including tokenHash.
9. It bcrypt-compares the presented raw token with the stored hash.
10. It rejects expired or mismatched sessions.
11. If the session is active, it marks the old session revoked with reason
    rotated and creates a replacement session in the same familyId.
12. The controller sets a new refreshToken cookie.
13. The response returns the new access token.

Response:

    {
      "accessToken": "eyJ..."
    }

The replacement refresh token is intentionally not returned in JSON.

Replay detection:

- A rotated refresh token must never be accepted again.
- If a token already marked rotated is presented, the service revokes all
  active sessions in that family with reason replay-detected.
- The request then fails and the client must log in again.
- Clients must serialize refresh calls. Two simultaneous refresh requests can
  cause one request to rotate the token and the other to look like replay.


10. LOGOUT FLOWS
----------------

10.1 Logout current browser/device
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

Endpoint:

    POST /auth/logout

No JSON body is required.

Server flow:

1. The controller reads the refreshToken cookie if present.
2. The service verifies the refresh JWT when possible.
3. It finds the matching stored session and compares the bcrypt hash.
4. It revokes the session family with reason logout.
5. The controller clears the refreshToken cookie.

This route is intentionally idempotent. Missing, expired, malformed, or
already-invalid cookies still result in a successful cookie-clear response.

Response:

    { "message": "Logged out successfully" }

10.2 Logout all devices
~~~~~~~~~~~~~~~~~~~~~~~~

Endpoint:

    POST /auth/logout-all

Required header:

    Authorization: Bearer <access-token>

Server flow:

1. JwtAuthGuard authenticates the access token.
2. The service identifies request.user.userId.
3. All non-revoked refresh sessions for the user are revoked with reason
   logout-all.
4. The current browser refreshToken cookie is cleared.

Response:

    {
      "message": "Logged out from all devices successfully",
      "revokedSessions": 2
    }

Already-issued access tokens are not revoked immediately and remain valid until
their short JWT expiry.


11. SIGNUP FLOW
--------------

Endpoint:

    POST /auth/signup

Request:

    {
      "email": "user@example.com",
      "password": "Password@123"
    }

Password validation requires:

- 8 to 32 characters.
- At least one uppercase letter.
- At least one lowercase letter.
- At least one number.
- At least one special character from @$!%*?&.

Server flow:

1. DTO validation runs.
2. Password is bcrypt-hashed.
3. UsersService.registerUser creates a user with email and password hash.
4. The service returns a success message.

Response:

    { "message": "Signup Successfull" }

Important current issue: Users.role is required in the schema, but signup does
not assign a role. Therefore public signup is not a safe plug-and-play flow and
may fail at database validation unless a role/default-role policy is added.
Signup also does not log the user in automatically.


12. USER ENDPOINTS
-----------------

POST /users/addUser

- Guard: JwtAuthGuard only.
- Payload:

    {
      "name": "Alice",
      "email": "alice@example.com",
      "password": "Password@123",
      "roleId": "ROLE_OBJECT_ID",
      "userStatus": "active"
    }

- name, email, password, and roleId are required by AddUserDto.
- The service validates the role ID, verifies the role exists, hashes the
  password, and creates the user.
- Current issue: any authenticated user can call this endpoint; AdminGuard is
  not applied.

GET /users/myprofile

- Guard: JwtAuthGuard.
- Payload: none.
- Uses request.user.userId.
- Loads the user and populates the role.
- Reads role.menuIds, loads assigned menus, loads ancestor menus, builds a tree,
  sorts by order, and returns a response containing user and role menu data.

Typical response shape:

    {
      "_id": "USER_ID",
      "name": "Alice",
      "email": "alice@example.com",
      "role": {
        "_id": "ROLE_ID",
        "name": "Manager",
        "menus": [
          {
            "_id": "MENU_ID",
            "title": "Dashboard",
            "slug": "dashboard",
            "type": "TAB",
            "parentId": null,
            "ancestors": [],
            "isActive": true,
            "order": 1,
            "children": []
          }
        ]
      },
      "userStatus": "active"
    }

GET /users/allUsers

- Guards: JwtAuthGuard, AdminGuard.
- Payload: none.
- Returns users with role and role privileges populated.

GET /users/fetch/:id

- Guards: JwtAuthGuard, AdminGuard.
- Returns one user using the same profile/menu-building logic.

PATCH /users/update/:id

- Guards: JwtAuthGuard, AdminGuard.
- Payload fields are optional:

    {
      "name": "Alice Updated",
      "email": "alice@example.com",
      "password": "NewPassword@123",
      "roleId": "ROLE_OBJECT_ID",
      "userStatus": "inactive"
    }

- A supplied password is hashed.
- A supplied roleId is validated and mapped to user.role.

DELETE /users/delete/:id

- Guards: JwtAuthGuard, AdminGuard.
- Deletes the selected user.


13. ROLE ENDPOINTS
------------------

POST /roles/addrole

- Guard: JwtAuthGuard only.
- Payload:

    {
      "name": "Manager",
      "menuIds": ["MENU_ID_1", "MENU_ID_2"]
    }

- Validates menu IDs and creates the role.
- Current issue: any authenticated user can create a role.

PUT /roles/updaterole/:id

- Guards: JwtAuthGuard, AdminGuard.
- Payload:

    {
      "name": "Manager Updated",
      "menuIds": ["MENU_ID_1"]
    }

- Replaces menuIds when supplied.

GET /roles/allrole

- No guard currently applied.
- Returns roles and constructed menu trees.
- Current issue: role/menu information is publicly readable.

DELETE /roles/deleterole/:id

- Guards: JwtAuthGuard, AdminGuard.
- A role used by users cannot be deleted.

PUT /roles/:roleId

- Guards: JwtAuthGuard, AdminGuard.
- Body:

    { "menuIds": ["MENU_ID_1", "MENU_ID_2"] }

- Replaces the role's assigned menus.

PATCH /roles/:id/admin-status

- Payload:

    { "isAdmin": true }

- Updates role.isAdmin.
- Critical current issue: no JwtAuthGuard or AdminGuard is applied. This route
  must be protected immediately.


14. MENU ENDPOINTS
-----------------

All current menu endpoints use JwtAuthGuard and AdminGuard.

POST /menu

Payload example:

    {
      "title": "Administration",
      "slug": "administration",
      "type": "TAB",
      "order": 1,
      "icon": "settings"
    }

For a child menu, parentId is required and type must be compatible:

    {
      "title": "Users",
      "type": "SECTION",
      "parentId": "TAB_ID",
      "order": 1
    }

The service normalizes titles/slugs, creates ancestors, validates parent type,
enforces sibling title/order uniqueness, and auto-generates a slug when absent.

GET /menu

- Returns the complete menu tree.
- Menus are nested under children and sorted by order.

GET /menu/:id

- Returns one menu document.

PUT /menu/:id

- Accepts any subset of CreateMenuDto fields.
- Supports title, slug, type, parentId, order, and icon changes.
- Prevents cycles and propagates changed ancestors to descendants in a
  transaction.

DELETE /menu/:id

- Refuses to delete a menu that still has children.

Role menu assignment does not itself copy menu documents. It stores menu IDs in
the role. User profile and role listing code later resolves those IDs and adds
ancestor menus to the returned tree.


15. PRIVILEGE ENDPOINTS
-----------------------

All current privilege endpoints use JwtAuthGuard and AdminGuard.

POST /privelleges/addprivelleges

Payload:

    { "name": "users.read" }

GET /privelleges/allprivelleges

- Returns all privilege documents.

PUT /privelleges/updateprivelleges/:id

Payload:

    { "name": "users.write" }

DELETE /privelleges/deleteprivelleges/:id

- Deletes a privilege document.
- Current service cleanup uses a `privileges` field while the role schema uses
  `privelleges`; this naming mismatch should be corrected.

Current authorization limitation: creating privilege records does not make an
endpoint permission-aware. There is no PermissionGuard or route metadata check.

17. CLIENT-SIDE REQUEST LIFECYCLE
----------------------------------

Recommended client sequence:

1. Login with credentials and store accessToken in memory.
2. Browser automatically retains the httpOnly refreshToken cookie.
3. Send accessToken on protected requests.
4. If a protected request returns 401 because the access token expired, send one
   POST /auth/refresh request with credentials included.
5. Replace the in-memory access token with the returned token.
6. Retry the original request once.
7. Serialize refresh calls with a mutex/queue. Never send concurrent refresh
   calls for the same browser session.
8. If refresh fails, clear local user state and redirect to login.
9. On sign-out, call POST /auth/logout.
10. After a suspected compromise or password recovery, call
    POST /auth/logout-all.

Example browser request:

    fetch('/auth/refresh', {
      method: 'POST',
      credentials: 'include'
    })


18. AUTHENTICATION VS AUTHORIZATION
-----------------------------------

Authentication answers: “Who is this caller?”

- Login verifies email and password.
- JWT access token represents the authenticated session.
- JwtAuthGuard verifies the bearer token and populates request.user.

Authorization answers: “What may this authenticated caller do?”

- JwtAuthGuard alone means any valid authenticated user.
- AdminGuard additionally loads the user's role and requires isAdmin=true.
- Menu assignment controls the menu tree returned to users, but is not itself a
  complete API authorization mechanism.
- Privilege records currently do not enforce endpoint permissions.

The frontend must never be trusted to enforce authorization. Hiding a menu item
is only a user-interface decision. The server must enforce every protected API
operation with guards and permission checks.


19. CURRENT SECURITY AND DESIGN GAPS
------------------------------------

The following issues were found during source review:

1. PATCH /roles/:id/admin-status is unprotected. A caller may be able to make a
   role administrative without authentication.
2. Labels CRUD is entirely public, including destructive operations.
3. /users/addUser and /roles/addrole allow any authenticated user rather than
   only an administrator or authorized manager.
4. Public signup creates no role even though Users.role is required.
5. Login checks the password but does not reject inactive or banned users. The
   status check exists during refresh only.
6. Privileges are stored but are not used for route authorization.
7. Role privilege cleanup uses a different spelling from the role field.
8. /roles/allrole is public.
9. CORS uses a reflected origin with credentials enabled; production should use
   an explicit allow-list.
10. Refresh cookie secure=false is unsuitable for HTTPS production.
11. JWT issuer and audience are not configured or validated.
12. Existing access tokens remain valid after logout-all, role changes, status
    changes, or user deletion until their expiry.
13. Throttle decorators are present, but ThrottlerModule configuration should be
    verified because it is not registered in AppModule.
14. Device names and user-agent values are metadata only and must not be used as
    identity proof.


20. RECOMMENDED TARGET DESIGN
-----------------------------

Priority 1: close immediate authorization holes

- Add JwtAuthGuard and AdminGuard to /roles/:id/admin-status.
- Protect label writes and decide whether label reads are public.
- Add AdminGuard or a dedicated permission guard to add-user and add-role.
- Protect /roles/allrole.

Priority 2: define account lifecycle policy

- Either remove public signup or assign a controlled default role.
- Reject inactive and banned users at login.
- Re-check user status on protected requests if immediate disablement is
  required.
- Revoke refresh sessions after password changes, account disablement, role
  changes, and account deletion.

Priority 3: implement real permission-based authorization

- Standardize spelling to `privileges` or `permissions`.
- Define stable permission names such as users.read, users.write,
  roles.manage, menus.manage, and labels.manage.
- Add route metadata and a PermissionGuard.
- Check permissions server-side; use menus only for navigation presentation.

Priority 4: harden deployment configuration

- Require JWT_SECRET at startup; remove the fallback outside development.
- Configure JWT issuer and audience.
- Set secure=true for HTTPS cookies.
- Make sameSite, domain, path, and maxAge environment-driven.
- Restrict CORS to known frontend origins.
- Add CSRF protection if cross-site cookies require SameSite=None.
- Configure trusted proxy handling before using request.ip for audit data.
- Enable and verify throttling for login, signup, and refresh.

Priority 5: improve verification and observability

- Add integration tests against a real MongoDB replica set.
- Test login, refresh rotation, replay detection, logout, logout-all, status
  changes, role changes, and permission denial.
- Add security audit events without recording passwords or raw tokens.
- Monitor repeated refresh replay and login failures.

22. SUMMARY
-----------

The intended security model is:

    email/password
        -> short-lived access JWT
        -> bearer authentication with JwtAuthGuard
        -> optional role/admin authorization with AdminGuard
        -> refresh cookie for rotating session renewal
        -> role menu assignment for navigation data

The refresh-token design is comparatively strong: raw refresh tokens are not
stored, sessions are hashed, rotation is transactional, families are tracked,
and replay revokes the family. The main remaining risk is authorization policy:
several routes are too permissive, privileges are not enforced, signup does not
assign a required role, and production cookie/CORS settings are not hardened.
