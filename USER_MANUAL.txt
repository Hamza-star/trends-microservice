User Management (NestJS) — User Manual

Overview
- Purpose: A modular NestJS microservice that manages users, roles, privileges, menus and authentication.
- Key technologies: NestJS, Mongoose, Passport (JWT), bcrypt, TypeScript.

Repository layout (important files)
- App entry: [src/main.ts](src/main.ts#L1)
- Module wiring: [src/app.module.ts](src/app.module.ts#L1)
- Auth: [src/auth](src/auth) — `auth.module.ts`, `jwt.strategy.ts`, `jwt.authguard.ts`, `authorization.policy.ts`
- Users: [src/users](src/users) — controller, service, and schema (includes `createdBy` tracking)
- Roles: [src/roles](src/roles) — controller, service, schema (includes `isSystem` flag)
- Permissions: [src/auth/permissions.constants.ts](src/auth/permissions.constants.ts#L1)

Authentication & Authorization
- JWT auth: tokens are validated by `JwtStrategy` (payload must include `sub`, `email`, `role`).
- Guards: `JwtAuthGuard` protects routes; `PermissionGuard` enforces required permissions via the `@RequirePermissions` decorator.
- Central policy: `AuthorizationPolicy` contains checks used across services:
  - `assertHasPermissions()` - verifies role has required permissions
  - `assertCanAssignRolePermissions()` - ensures actor can assign permissions they possess (unless actor is SUPER_ADMIN)
  - `assertRoleModifiable()` - enforces restrictions when modifying roles (see SUPER_ADMIN rules below)

SUPER_ADMIN and system role protections
- The `SUPER_ADMIN` role is reserved and case-insensitive. It cannot be created or renamed to `SUPER_ADMIN` by non-super-admins.
- Only a user whose role is `SUPER_ADMIN` may:
  - modify a role whose name is `SUPER_ADMIN`
  - assign the `SUPER_ADMIN` role to another user
  - modify roles that are flagged with `isSystem: true`
- These protections live in `AuthorizationPolicy` and are enforced in the roles and users services. Attempting to bypass returns a `BadRequestException`.

User/Role visibility rules
- Users created by an admin are tracked using the `createdBy` ObjectId on the `Users` schema.
- `findAll()` for users excludes the requesting user and restricts non-super-admins to seeing only users they created.
- `getAllRoles()` returns all roles to `SUPER_ADMIN`; non-super-admins only see roles they created.

Mongoose notes & deprecations
- Use `returnDocument: 'after'` instead of `{ new: true }` for `findByIdAndUpdate` and `findOneAndUpdate` (repository updated accordingly).

Environment variables
- `MONGODB_URI` — MongoDB connection string (defaults to mongodb://127.0.0.1:27017/user-management-nestjs)
- `JWT_SECRET` — secret used to sign JWTs (default `dev-jwt-secret` if unset)

Common requests and troubleshooting
- "Auth guard failing" stacktrace from `@nestjs/passport` usually means the JWT is missing, expired, or the `JWT_SECRET` is wrong. Check Authorization header `Bearer <token>` and confirm `JWT_SECRET`.
- If you see Mongoose warnings about `new: true` — update code to `returnDocument: 'after'` (already applied in this repo).
- When a role or user update silently succeeds but should be blocked, verify the requesting user's role in the JWT payload and that the `AuthorizationPolicy` checks are present in the service method.

Adding a permission or role
1. Add a new entry to `src/auth/permissions.constants.ts`.
2. Use the constant value in controllers via `@RequirePermissions('your.permission')`.
3. Ensure any role creation or permission assignment flows call `authorizationPolicy.assertCanAssignRolePermissions()` so actors can't assign permissions they do not possess.

Developer notes
- Circular module dependencies are resolved using `forwardRef()` where modules import each other (e.g., `UsersModule` and `RolesModule`).
- Schema fields of note: `Roles.isSystem` (boolean), `Roles.createdBy`, `Users.createdBy`.
- Tests: unit tests live alongside controllers/services as `*.spec.ts` files. Use `npm test` to run.
